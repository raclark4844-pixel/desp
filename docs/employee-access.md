# AP Spartan employee access

Employees sign in at `/login` with their user ID or email and password. There is no public registration. Ryan Clark is the initial administrator, provisioned separately from customer portal records. Administrators use `/admin/users` to create employee accounts, assign administrator privileges, disable/enable accounts and set temporary passwords. Passwords contain 12–128 characters; temporary passwords must be changed at `/account` before any customer or campaign access. Administrators distribute temporary credentials privately; no emails are sent by these screens.

Password hashes use Node's scrypt with a per-password random 16-byte salt (N=131072, r=8, p=1). Sessions use random 32-byte opaque tokens; only SHA-256 token hashes are stored in Neon. Cookies are HttpOnly, Secure in production and SameSite=Strict, with an eight-hour absolute expiration. Writes require same-origin requests. Every employee request checks the current account status and password-change requirement. Logout, password changes, administrator resets and role/status changes revoke sessions. Authentication uses shared database attempt limits per login and IP over fifteen minutes. Employee-account changes and successful sign-ins are audited without password material. There is no password retrieval or display feature.

The shared internal API key remains for machine operations. Legacy operations cookies remain read-only; they cannot administer employees or save linked campaign drafts. Employee sessions authorize customer lookup, draft creation and compliance evidence review; they do not grant paid provider-worker execution or outreach. Employee identities are recorded for campaign creation and evidence. Campaign pages now require employee sign-in and the draft API rejects unauthenticated public creation.

The initial administrator password is generated locally and delivered in a restricted local file outside the Git repository. It must be changed on first login. Keep the new password in a password manager. If all administrators lose access, an authorized database operator must reset an administrator password using the same hashing and session-revocation procedure; there is no unauthenticated recovery endpoint. MFA and external identity-provider SSO are not included in this release.

Validation covers correct/incorrect passwords, salted hashing, session cookies, employee versus administrator authorization, first-use password changes, disabled accounts, self-demotion protection, reset and logout revocation, existing guardrails, Prisma validation, TypeScript and production build. Apply the additive employee tables migration to an isolated Neon branch before production.
